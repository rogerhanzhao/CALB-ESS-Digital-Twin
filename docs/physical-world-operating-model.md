# 物理世界业务模型与平台范围校准

- 适用项目：CALB ESS Digital Twin
- 记录版本：V0.1
- 状态：**产品范围已由 Alex.Z 确认，技术实施持续交叉审核**
- 目的：校准平台的真实业务频率、数据来源、仿真边界和系统复杂度

## 1. 核心定位

本平台不是面向大量普通用户、持续产生大量仿真任务的通用计算平台。

它服务于低频但高价值的工程活动：当新电芯、新产品或新系统方案出现时，结合物理测试数据、
PyBaMM 的模型要求和行业工况，生成少量标准仿真结果并保存。后续获得新测试数据时，形成新的
数据集和标定版本，重新运行同一套标准工况，并发布经过审核的新结果版本。

因此，平台的中心对象不是“任务吞吐量”，而是：

> 产品版本、物理样品、测试数据集、模型标定、标准工况、结果版本和工程审核记录。

## 2. 事实与模型的关系

物理测试数据是产品行为的事实基础，PyBaMM 和半经验模型是解释、标定与外推工具。

PyBaMM 适合：

- 检查电化学行为及参数组合是否合理；
- 分析温度、倍率、SOC 和 DoD 对运行状态的影响；
- 在测试覆盖不足的位置提供物理约束；
- 形成具有可解释性的中间变量和参考曲线。

PyBaMM 不应：

- 脱离产品实测数据直接生成长期质保曲线；
- 用公开 LFP 参数集代替具体 CALB 产品参数；
- 将单次 SPMe 放电结果解释为 SOH；
- 自动覆盖已经审核或批准的工程结果。

当前 `pybamm:Prada2013` 仅用于验证真实电化学计算链路。它不是 CALB 量产电芯参数集，
不得进入正式产品质保结论。

## 3. 真实工程工作流

```text
新产品 / 新方案
        ↓
建立产品版本与物理样品记录
        ↓
导入测试数据
        ↓
数据质量检查、清洗与异常标记
        ↓
基于测试数据标定模型
        ↓
运行少量版本化标准工况
        ↓
工程师审核并批准结果版本
        ↓
新增测试数据到达
        ↓
生成新数据集版本并重新标定
        ↓
复跑相同标准工况并比较新旧结果
        ↓
批准新版本；旧版本继续保留
```

## 4. 版本原则：追加而非覆盖

“更新已有仿真结果”不表示直接修改旧结果。应产生新的数据集、标定和结果版本：

```text
产品 P1
├── 数据集 D1
│   └── 标定 M1
│       └── 标准工况结果 R1
└── 数据集 D2（增加新测试数据）
    └── 标定 M2
        └── 标准工况结果 R2
```

页面默认展示最新批准版本，同时必须能够回看 R1 与 R2，并解释变化来源：

- 测试数据增加或修订；
- 数据清洗规则变化；
- 参数拟合或模型结构变化；
- PyBaMM、求解器或依赖版本变化；
- 代码 revision 变化；
- 标准工况定义变化。

任何已批准结果均不可静默覆盖。重新计算必须生成新的 run 和 result version。

## 5. 建议的核心数据对象

| 对象 | 责任 |
|---|---|
| `products` | 电芯或系统产品、型号、设计版本和额定参数 |
| `test_samples` | 样品编号、批次、制造信息、测试机构和设备 |
| `test_datasets` | 原始/清洗数据、测试类型、质量状态和数据版本 |
| `calibrations` | 使用的数据集、模型参数、拟合误差、适用边界和审核状态 |
| `standard_scenarios` | 固定、命名且版本化的行业或项目标准工况 |
| `simulation_runs` | 一次可复现的计算执行记录 |
| `result_versions` | 结果版本、审核状态、批准时间和批准人 |
| `artifacts` | 曲线、日志、报告、运行环境和文件校验和 |

结果状态至少包括：`draft`、`under_review`、`approved`、`superseded`、`rejected`。

## 6. 首批标准工况建议

初期建议控制在 4–6 个标准工况，而不是建立大量任意任务：

1. 25°C、1 次/日、90% DoD：标准基准工况；
2. 35°C、1 次/日、90% DoD：高温工况；
3. 15°C、1 次/日、90% DoD：低温工况；
4. 25°C、2 次/日、90% DoD：高吞吐工况；
5. 25°C、1 次/日、70% DoD：保守运行工况；
6. 项目工况：客户或实际调度曲线。

工况必须版本化，例如 `ESS-STD-25C-1CPD-90DOD / V1`。SOC 窗口等定义发生变化时，
必须创建 V2，不得修改 V1 的含义。

## 7. 对现有架构的审核结论

| 已有设计 | 结论 | 调整方式 |
|---|---|---|
| Web 控制面 | 保留 | 页面重心改为产品、数据、标定、工况和结果版本 |
| 后台持续执行 | 保留 | 支持关闭页面后继续运行即可 |
| Pydantic 契约 | 保留 | 扩展到数据集、标定和结果审批契约 |
| PyBaMM SPMe runner | 保留 | 作为参考电化学计算，不作为寿命结论 |
| SQLite 租约与 checkpoint | 租约简化保留，checkpoint 作为必需能力 | 服务本地任务接管、长时计算恢复和可复现执行 |
| Docker worker | 保留 | 冻结计算环境；`approved` 结果必须产自容器并记录 image digest（见导入与质量规范 §8），本地探索性运行不强制 |
| `scenarios/runs/artifacts` | 保留并扩展 | 增加产品、样品、数据集、标定和结果版本 |
| 云队列、R2、多 worker 扩容 | 暂缓 | 有明确多人/远程部署需求后再引入 |
| K8s 与复杂配额体系 | 当前不采用 | 不符合低频少量标准仿真的业务规模 |

## 8. 硬件与部署边界

在低频、少量标准工况模式下，当前个人工作站足以承担早期研发计算。CPU、内存和稳定的本地
存储比 GPU 更关键。正式多人使用时可将元数据迁移至 PostgreSQL，将原始测试数据、曲线和审计
包存入对象存储；在此之前不应优先投入复杂的云端调度系统。

后台进程必须满足：

- 页面关闭后任务继续执行；
- 计算中断后能够从 checkpoint 恢复或安全重跑；
- 每次运行记录代码、参数、数据和依赖版本；
- 桩、公开参数参考结果和正式产品结果能够永久区分。

## 9. 修订后的近期优先级

在进入真实 SOH 模型开发之前，应依次完成：

1. 冻结产品、样品、测试数据集、标定和标准工况的数据模型；
2. 定义测试数据导入格式、单位、质量检查和异常标记规则；
3. 由 Alex.Z 确认首批标准工况及其版本；
4. 定义结果的草稿、审核、批准和废弃流程；
5. 建立同一标准工况下新旧数据集和新旧结果的差异比较；
6. 完成上述基础后，再进入真实 SOH 标定与长期外推。

## 11. 持续开发与无停摆原则

Alex.Z 已确认本文件描述的岗位工作流是平台的长期产品目标。项目不以完成某个页面、PR 或
里程碑作为停止条件；阶段完成或路线暂时不明确时，Claude 与 CODEX 自动进入下一轮平台审核，
从下列方向选择风险最高、能够验证且不与对方所有权冲突的工作继续推进：

1. 真实岗位工作流是否完整，页面是否能够完成产品、样品、数据、标定、标准工况和结果审核；
2. 物理量、单位、边界和模型假设是否正确，是否存在把参考计算误当正式结论的风险；
3. 数据、参数、代码、依赖和结果版本是否可追溯、可复现且不可静默覆盖；
4. 导入、异常数据、计算中断、恢复、失败重试和审批状态是否有测试与明确行为；
5. UI、API、计算面、部署和硬件说明是否存在影响实际使用的缺陷或不必要复杂度；
6. 已知缺陷、测试缺口、性能问题和安全问题是否能够复现并按风险排序处理。

持续开发不等于持续增加功能。不得为了保持忙碌而编造数据、指标、模型能力或业务需求。
每轮工作必须产生可核验的代码、测试、审核结论、文档或明确交棒记录；只有全部安全工作都被
真实外部依赖或必须由 Alex.Z 作出的产品决定阻塞时才允许等待。等待产品决定优于用臆造的值
填补它。

协同交棒统一记录 `NEXT OWNER`、`NEXT ACTION`、`EVIDENCE` 和 `BLOCKER`。一方等待另一方的
跨边界输入时，应继续自己职责范围内的非冲突工作，避免双方互相等待。

本记录授权在上述产品边界内持续推进平台基础、数据闭环、计算验证、SOH 标定准备和缺陷清理。
正式产品寿命或质保结论仍必须以真实测试数据、批准的标定版本和工程审核为前提。
